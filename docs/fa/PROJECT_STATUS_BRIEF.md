# گزارش وضعیت اجرایی پروژه NextOps

[English](../en/PROJECT_STATUS_BRIEF.md) · [فهرست مستندات](INDEX.md) · [وضعیت پروژه](../PROJECT_STATE.md) · [کار بعدی](../NEXT_TASK.md)

به‌روزرسانی: ۳۰ شهریور ۱۴۰۵، برابر با ۲۱ سپتامبر ۲۰۲۶

این گزارش، جمع‌بندی آمادهٔ ارائه از پیشرفت‌های تأییدشده و کارهای باقی‌مانده است. هر چهار سرور
Ubuntu 24.04 از مرحلهٔ صلاحیت‌سنجی عبور کرده‌اند و بسته‌های موردنیاز هر نقش روی آن‌ها آماده شده
است. محیط اجرای محلی مدل روی CPU و فایل مدل نیز در یک آزمون محدود و احرازهویت‌شده با موفقیت اجرا
شده‌اند. سرویس‌های محصول عمداً متوقف مانده‌اند تا پیکربندی تولید، یکپارچه‌سازی، بازیابی و پذیرش
آفلاین به‌صورت کنترل‌شده انجام شود.

## جمع‌بندی مدیریتی

NextOps از مرحلهٔ صرفاً معماری عبور کرده است. مخزن اکنون پایهٔ آزمودهٔ برنامه و سرویس inference را
دارد؛ چهار سرور نقش‌محور بررسی شده‌اند؛ بسته‌های لازم نصب شده‌اند؛ و مدل محلی روی سرور AI پاسخ تازهٔ
فارسی و انگلیسی تولید کرده است. با این حال، سامانه هنوز استقرار تولیدیِ قابل بهره‌برداری نیست. پایگاه
دادهٔ تولید و Zabbix هنوز مقداردهی اولیه نشده‌اند، برنامه و connector استقرار نیافته‌اند و آزمون
سرتاسری با اینترنت قطع‌شده انجام نشده است.

## کارهای انجام‌شده

### معماری نیازمندی‌ها و مرزهای ایمنی

- مالک، مرحلهٔ صفر، مسیر تحویل 1A تا 1E و ADRهای 0001 تا 0006 را پذیرفته است.
- استقرار اولیه چهار ماشین مجازی دارد: برنامه، AI محلی، connectorهای فقط‌خواندنی و Zabbix مستقل.
  بودجهٔ آغازین تأییدشده ۴۰ vCPU، حافظهٔ ۱۸۴ GiB و دیسک مجازی ۹۸۰ GiB است.
- تولید پاسخ باید روی CPU محلی انجام شود. سامانه به GPU وابسته نیست و fallback ابری ندارد. مدل به
  اطلاعات ورود زیرساخت یا اختیار تأیید عملیات دسترسی پیدا نمی‌کند.
- مرحلهٔ یک فقط‌خواندنی است. هر تغییر در مراحل بعد به policy قطعی، تأیید دقیق همان عملیات، اجرای
  جداشده و audit نیاز دارد.

### پایهٔ مخزن و برنامه

- پروژهٔ Python دارای lockfile و مرزهای نوع‌دار domain و application است.
- مرحلهٔ 1A شامل bootstrap، login و recovery با Argon2id؛ session غیرشفاف و hash‌شده؛ استخراج
  organization، environment، role و scope در سمت سرور؛ PostgreSQL و migrationهای Alembic؛ runهای
  ماندگار و idempotent؛ lease منقضی‌شونده؛ audit محدود به append؛ و FastAPI احرازهویت‌شده است.
- مرحلهٔ 1B قرارداد مستقل `LLMProvider`، مرزهای احرازهویت‌شدهٔ inference، adapter فقط-loopback برای
  llama.cpp، زمان‌بندی یک درخواست فعال و دو درخواست در صف، حدود ورودی و خروجی، مدیریت timeout و
  cancellation، readiness امن و خطای صریح overload یا dependency را پیاده کرده است.
- چهار پروندهٔ استقرار معتبرشده با schema و installerهای محافظت‌شده، تحویل عمومی هر نقش را مشخص
  می‌کنند؛ نشانی خصوصی، credential، fingerprint و log خام وارد Git نمی‌شود.

### صلاحیت‌سنجی سرورها و آماده‌سازی بسته‌ها

- هر چهار مهمان جایگزین تمیز، کنترل کلید میزبان SSH، احراز هویت فقط با کلید، رد ورود مستقیم root،
  بررسی منابع و mount، همگامی زمان، VMware Tools و سلامت سیستم را با موفقیت گذرانده‌اند.
- هر چهار مهمان Ubuntu 24.04.5 LTS دارند؛ unit خراب، update یا reboot معلق ندارند؛ UFW فعال است و
  جز SSH هیچ listener عمومی TCP وجود ندارد.
- بسته‌ها از زنجیرهٔ proxy سخت‌گیرانهٔ موجود و بدون ارتقای کلی سیستم‌عامل نصب شدند. شروع خودکار
  سرویس و ایجاد خودکار cluster در PostgreSQL مسدود شد.
- میزبان برنامه PostgreSQL 16.15 و Nginx 1.24 دارد. میزبان AI دارای GCC 13.3، CMake 3.28،
  Ninja 1.11، OpenBLAS 0.3.26 و uv 0.12.17 است. میزبان connector از virtual environment در
  Python 3.12 پشتیبانی می‌کند. میزبان پایش نیز Zabbix 7.0.30، PostgreSQL 16.15، Nginx 1.24،
  PHP 8.3.6، frontend، scriptهای SQL و Agent 2 را دارد.
- هویت‌های بدون login و مسیرهای محافظت‌شدهٔ هر نقش ساخته شده‌اند. سرویس‌های محصول، پایگاه و وب
  طبق برنامه همچنان inactive و disabled هستند.
- Docker نصب نشد، زیرا طراحی فعلی بر package بومی و systemd متکی است و container socket مرز اعتماد
  را بی‌دلیل گسترش می‌دهد.

### شاهد مدل محلی روی CPU

- revision ثابت llama.cpp در حالت Release با تنظیم native CPU، OpenMP و OpenBLAS و بدون پیوند GPU
  ساخته شد. checksum فایل اجرایی ارتقایافته در manifest مربوط به inference ثبت شده است.
- فایل ثابت `Qwen3-8B-Q4_K_M.gguf` برابر ۵٬۰۲۷٬۷۸۳٬۴۸۸ بایت است. SHA-256 آن پیش و پس از انتقال
  به حجم محافظت‌شدهٔ مدل با مقدار موردانتظار برابر بود.
- سرویس موقت و احرازهویت‌شده فقط روی loopback، با یک slot، context برابر 8K، لایهٔ GPU برابر صفر
  و Web UI غیرفعال اجرا شد. سرویس در ۷ ثانیه شروع سرد داشت، `READY` را در ۶۳۰ میلی‌ثانیه و `آماده`
  را در ۱۴۳۱ میلی‌ثانیه برگرداند و بدون process یا listener باقی‌مانده متوقف شد.
- این نتیجه فقط شاهد یک smoke test محدود است؛ benchmark کیفیت، آزمون بار پایدار، پذیرش سرویس تولید
  یا اثبات کارکرد با اینترنت قطع‌شده محسوب نمی‌شود.

### اعتبارسنجی انجام‌شده

- format، lint، بررسی سخت‌گیرانهٔ type، مستندات، پرونده‌های استقرار، artifactهای inference و
  installerها برای revision بازبینی‌شده با موفقیت اعتبارسنجی شدند.
- روی desktop، هر ۷۱ آزمون non-integration قبول و پنج آزمون پایگاه به‌دلیل نبود URL محلی PostgreSQL
  به‌درستی skip شدند.
- روی سرور برنامه، همان revision از format، lint و type عبور کرد؛ هر ۷۱ آزمون non-integration و هر
  پنج آزمون integration روی cluster موقت و جداشدهٔ PostgreSQL 16.15 قبول شدند. cluster پس از آزمون
  حذف شد.

## کارهای باقی‌مانده

### سرویس تولید inference در مرحلهٔ 1B

پیکربندی متعلق به root و ارجاع امن secretها تهیه و بازبینی شود؛ unit سرویس `nextops-ai` در systemd
نصب شود؛ اتصال فقط روی loopback بماند؛ و کنترل CPU و حافظه اعمال شود. احراز هویت، health، restart،
log، overload، cancellation، timeout و rollback باید آزموده شوند. ارزیابی نسخه‌دار فارسی و انگلیسی
باید کیفیت، latency، token، حافظه، CPU، thread و صف را ثبت کند. شروع سرد با اینترنت قطع و شبکهٔ داخلی
مجاز نیز باید تکرار و مستند شود.

### استقرار برنامه در مرحلهٔ 1A

release آفلاین برنامه بسته‌بندی شود؛ PostgreSQL 16 روی mount اختصاصی مقداردهی شود؛ roleهای
کم‌دسترسی ساخته شوند؛ migration اجرا شود؛ هویت محلی bootstrap شود؛ و سرویس‌های API و worker مستقر
شوند. سپس Nginx و TLS، رابط مرورگر، تحویل secret، backup، restore و rollback پیش از اعلام آمادگی
استقرار تکمیل شوند.

### پیش‌نیاز Zabbix

پایگاه PostgreSQL مربوط به Zabbix روی mount اختصاصی مقداردهی و schema وارد شود. Zabbix Server،
Nginx، PHP-FPM و Agent 2 پیکربندی و مسیر بازیابی مدیر محلی برقرار شود. self-monitoring، سیاست اولیهٔ
retention بر اساس رشد واقعی و هویت API فقط‌خواندنی و محدود نیز لازم‌اند. هیچ سرویس پایشی نباید خارج
از دامنهٔ شبکهٔ مصوب در دسترس قرار گیرد.

### connector فقط‌خواندنی و نخستین پاسخ کاربردی

gateway و runner جداشدهٔ Zabbix روی سرور connector مستقر شوند. توکن محدود Zabbix فقط در اختیار همان
runner باشد؛ تنها روش‌های read فهرست‌شده مجاز باشند؛ اندازه و زمان پاسخ محدود شود؛ شمارش‌ها در کد
انجام شوند؛ و متن جمع‌آوری‌شده شاهد غیرقابل‌اعتماد تلقی شود. سپس باید مسیر کامل سؤال تازهٔ فارسی و
انگلیسی، شاهد جاری Zabbix، تجمیع قطعی، توضیح مدل محلی، منبع، زمان مشاهده، دامنه و audit محدود به
append نمایش داده شود.

### پذیرش آفلاین و بازیابی

مرحلهٔ 1E با قطع WAN از هر چهار سرور و یک client تازه انجام شود. شروع سرد PostgreSQL، Zabbix،
برنامه، connector و مدل؛ ورود تازهٔ محلی؛ رفتار در برابر توکن باطل، مقصد خارج از دسترس و دادهٔ
قدیمی؛ کمبود فضا؛ سقف منابع؛ backup مستقل؛ آزمون restore؛ و rollback نسخه باید اثبات شوند. موارد
مستند ZBX-01 تا ZBX-08 و OFF-01 تا OFF-10 مرتبط فقط با نتیجهٔ واقعی و ثبت‌شده پذیرفته می‌شوند.

## ترتیب پیشنهادی ادامهٔ کار

1. سرویس AI تولیدی شود و ارزیابی دوزبانه و آفلاین مرحلهٔ 1B کامل شود.
2. پایگاه، API، worker، reverse proxy، TLS، secret، backup و restore برنامه بسته‌بندی و مستقر شوند.
3. Zabbix مقداردهی و هویت API فقط‌خواندنی و محدود ایجاد شود.
4. connector مستقر و خواندن زنده، محدود و نسخه‌سازگار مرحلهٔ 1C کامل شود.
5. پاسخ مستند مرحلهٔ 1D نمایش داده شود و پذیرش آفلاین و بازیابی مرحلهٔ 1E پایان یابد.

## نتیجهٔ قابل ارائه

زیرساخت و پایهٔ نرم‌افزار برای آغاز استقرار کنترل‌شدهٔ سرویس‌ها آماده است. پروژه اکنون سرورهای
تأییدشده، بسته‌های نصب‌شدهٔ هر نقش، پایهٔ مخزن آزموده و artifact عملیاتی مدل محلی روی CPU دارد.
کار باقی‌مانده شامل پیکربندی تولید، مقداردهی سرویس‌های stateful، اتصال فقط‌خواندنی، اثبات بازیابی و
پذیرش کامل آفلاین است. تا عبور از این دروازه‌ها، توصیف دقیق پروژه «آماده‌شده و تا حدی
اعتبارسنجی‌شده» است، نه «آمادهٔ بهره‌برداری تولیدی».
