# داده، گردش‌کار ماندگار، شواهد و API

[English](../en/DATA_API.md) · [فهرست](INDEX.md)

**وضعیت: پایهٔ ماندگار 1A همراه پیوند مستقرشدهٔ بررسی زنده در 1D.** مبنا بخش‌های ۱۱، ۱۶، ۱۷ و
۲۰ مشخصات اصلی است. بخش پیاده‌شده عمداً محلی، تک‌سازمانی و فقط‌خواندنی است. پاسخ عمومی و بدون
شاهد، مستقل باقی مانده و بررسی زندهٔ Zabbix اکنون از همان مدل اجرای ماندگار و ممیزیِ فقط‌افزودنی
استفاده می‌کند.

## بخش پیاده‌شدهٔ 1A

migration با شناسهٔ `0001_durable_app` جدول‌های PostgreSQL برای سازمان، محیط، هدف، هویت،
session غیرشفاف، run، lease کارگر و رخداد ممیزی را می‌سازد. قید پایگاه مرز آغازین یک
سازمان، کلید خارجی محدود، idempotency اجرا، حالت‌های معتبر و اعتبار lease را اعمال می‌کند.
سه role گروهی `nextops_migrator`، `nextops_app` و `nextops_support_ro` ساخته می‌شوند. role
برنامه audit را append می‌کند اما حق update/delete ندارد و trigger پایگاه تغییر رکورد
ممیزی حتی توسط مالک جدول را رد می‌کند. login role استقرار و تحویل secret هنوز کار محیط
استقرار است.

سطح HTTP پیاده‌شده:

| روش و مسیر | احرازهویت | رفتار |
|---|---|---|
| `GET /healthz` | ندارد | فقط زنده‌بودن process؛ آمادگی وابستگی را ادعا نمی‌کند |
| `POST /api/v1/bootstrap` | header یک‌بارمصرف استقرار | سازمان، محیط، مدیر، هدف fixture، audit و نخستین session را اتمی می‌سازد |
| `POST /api/v1/login` | نام کاربر/رمز محلی | bearer token غیرشفاف و منقضی‌شونده می‌دهد؛ فقط SHA-256 آن ذخیره می‌شود |
| `POST /api/v1/recovery` | header محافظت‌شدهٔ بازیابی | رمز و نسخهٔ credential مدیر را عوض و همهٔ sessionهای قبلی را لغو می‌کند |
| `GET /api/v1/me` | bearer | نقش و scope را از session سمت سرور می‌سازد |
| `GET /api/v1/assistant/ready` | bearer | آمادگی محدود سرویس مدل محلی را بدون افشای credential آن برمی‌گرداند |
| `POST /api/v1/assistant/generate` | bearer | پاسخ عمومی مدل محلی را بدون شاهد پایشی برمی‌گرداند |
| `GET /api/v1/monitoring/summary` | bearer | خلاصهٔ محدود و فقط‌خواندنی جاری Zabbix را دریافت می‌کند |
| `POST /api/v1/investigate` | bearer | اجرای محدود به دامنه را ماندگار می‌کند، شاهد را می‌گیرد، پاسخ محلی می‌سازد و نتیجه، هش شاهد و ممیزی تکمیل را اتمی ثبت می‌کند |
| `POST /api/v1/runs` | bearer و `Idempotency-Key` | اجرای fixture فقط‌خواندنی را مجاز، ماندگار و lease می‌کند و نتیجهٔ صریح fixture می‌دهد |
| `GET /api/v1/runs/{run_id}` | bearer | فقط در سازمان و محیط ساخته‌شده در سرور می‌خواند |

رمز با Argon2id نگه‌داری می‌شود. tokenهای session و lease غیرشفاف‌اند، یک بار برگردانده و
به‌شکل hash ذخیره می‌شوند. کلید idempotency تکراری فقط برای intent canonical یکسان همان
run را می‌دهد و برای intent متفاوت conflict است. lease منقضی پس از restart قابل بازیابی
است. تغییر وضعیت و audit لازم در یک تراکنش‌اند؛ خرابی پایگاه یا audit موفقیت کاذب تولید
نمی‌کند. خطا code، کلید پیام، retryability، جزئیات و correlation ID ثابت دارد.

نتیجهٔ fixture اولیه همچنان صریح، قدیمی و غیرزنده است. بررسی زنده پیش از تماس با اتصال یا مدل،
اجرای خود را می‌سازد. در حالت موفقیت، `MonitoringSummary` محدود، SHA-256 معیار و مرجع
`run-evidence:<run_id>` آن، نتیجهٔ دارای نوع مدل محلی، شناسه‌های دامنه و شناسهٔ رویداد ممیزی تکمیل
در نتیجهٔ اجرا نگه‌داری می‌شوند. تغییر وضعیت و درج ممیزیِ فقط‌افزودنی در یک تراکنش انجام می‌شود.
در حالت شکست نیز فقط کد خطا، کلید پیام و امکان تکرار ثبت و ممیزی می‌شود و پاسخ خام وابستگی وارد
پایگاه نمی‌شود. API و پنل شناسه‌های اجرا، شاهد و ممیزی را نشان می‌دهند و بازیابی محدود به دامنه،
همان نتیجهٔ ماندگار را برمی‌گرداند.

## مدل ذخیره‌سازی

PostgreSQL مرجع معتبر وضعیت است و از پایگاه داده‌هایی که NextOps مدیریت می‌کند جدا می‌ماند. برای هر گروه، شناسهٔ ثابت، کلید خارجی، قید یکتا، index، دورهٔ نگهداری و قواعد دسترسی تعریف شوند.

| گروه | رکوردها و ارتباط‌ها |
|---|---|
| هویت و دامنه | سازمان، محیط، کاربر، نقش و مجوز محدود |
| موجودی | تجهیز، مقصد مجاز، قابلیت و نسخه، ارجاع اطلاعات ورود |
| اتصال | ثبت اتصال‌دهنده، نسخه و قابلیت ابزار |
| گردش‌کار | رخداد و رویداد، اجرا، گام، کار ماندگار، اجارهٔ کار و نقطهٔ ثبت پیشرفت |
| شواهد | منبع، تجهیز و دامنه، زمان مشاهده و جمع‌آوری، ارجاع محتوای پالایش‌شده و تازگی |
| اقدام | پیشنهاد، تأیید، تلاش اجرا و نتیجهٔ بررسی |
| دانش | سند، قطعهٔ متن، بردار، گفت‌وگو، حافظهٔ رخداد و گره و یال توپولوژی |
| حاکمیت | ممیزی و نسخهٔ مدل، پرامپت، سیاست و انتشار |

رابطهٔ مفهومی چنین است: سازمان محیط و کاربرِ دارای دامنه دارد؛ محیط شامل تجهیزات است؛ رخداد به تجهیزات درگیر و اجراهای گردش‌کار مرتبط می‌شود؛ هر اجرا گام و شاهد دارد؛ پیشنهاد به اقدام و مقصد دقیق و در صورت نیاز به تأیید وصل می‌شود؛ هر تلاش اجرا به پیشنهاد و شاهد بررسی نتیجه ارجاع می‌دهد. ممیزی نیز عامل، مقصد و عملیات مربوط را مشخص می‌کند. این توصیف schema اجرایی نیست.

زمان داخلی UTC باشد؛ منطقهٔ زمانی منبع، زمان جمع‌آوری و احتمال اختلاف ساعت حفظ شود. دادهٔ حساس به مجوز باید دامنه داشته باشد. نقش‌های پایگاه داده طوری محدود شوند که API یا برنامه‌ریز نتواند با نوشتن آزاد در پایگاه، تأیید اجرایی جعل کند.

بررسی فقط‌خواندنی از تأیید تغییر عبور نمی‌کند، اما همچنان مجوز و ممیزی لازم دارد. پیشرفت پیش و پس از اثر خارجی ثبت شود. در صورت نیاز ایجاد کار و outbox تراکنشی، اجارهٔ worker، heartbeat و تشخیص تکرار به‌کار رود. اجرای دقیقاً یک‌باره میان تجهیز و PostgreSQL ادعا نشود. پیش از تکرار تغییرِ احتمالاً اجراشده، وضعیت مقصد بررسی شود. لغو محلی تضمین لغو راه دور نیست.

زمان کل، تعداد فراخوانی مدل و ابزار، توکن، بایت، پراکندگی کار و تکرار محدود شوند. نمونهٔ شش فراخوانی مدل و بیست فراخوانی ابزار در مشخصات، نقطهٔ شروع آزمایش است، نه مقدار بهینهٔ اندازه‌گیری‌شده.

## شواهد، بازیابی و توپولوژی

منشأ، نسخهٔ منبع، زمان منبع و جمع‌آوری، هش محتوا، دامنهٔ مجوز و نشانهٔ پالایش یا ناقص بودن ثبت شوند. دسترسی پیش از بازیابی و هنگام ارائهٔ شاهد کنترل شود. رخداد قدیمی اثبات وضعیت فعلی نیست. تا حد امکان تاریخچهٔ خام پایش در سامانهٔ اصلی باقی بماند.

توپولوژی ابتدا با یال‌های رابطه‌ای شامل نوع رابطه، منبع، تازگی و وضعیت مشاهده‌شده یا استنباطی ساخته شود. فقط سند تغییرکرده دوباره نمایه‌سازی شود. نسخهٔ قطعه و مدل بردارسازی و ابعاد ثبت شوند. تغییر مدل بردارسازی نیازمند سازگاری نمایه است. cache نیز باید دامنه و تازگی را رعایت کند.

خروجی تحلیل علت ریشه‌ای باید نشانه‌ها، شواهد، علت‌های احتمالی، شواهد موافق و مخالف، اطمینان همراه دلیل، مجهولات، گام تشخیصی بعدی و اقدام پیشنهادی با ریسک و تأیید و بررسی نتیجه را جدا کند. عنوان «علت تأییدشده» فقط با شاهد کافی به‌کار رود. احتمال عددیِ بدون اعتبارسنجی تولید نشود.

## رفتار پیاده‌شده و برنامهٔ بعدی API

مسیرهای بالا در `/api/v1` پیاده شده‌اند. agent، مدیریت connector و تجهیز، رخداد، مرور جداگانهٔ
شاهد و audit، تأیید، مدیریت کاربر/role، تنظیمات، streaming، pagination، cancellation و ورودی alert
هنوز برنامه‌اند و پیاده نشده‌اند. اگر کد قدیمی بعداً وارد شد، حفظ مسیرهای قبلی
تصمیم سازگاری صریح می‌خواهد. endpointهای زنده‌بودن و آمادگی نباید جزئیات حساس عمومی بدهند.

درخواست طولانی یک اجرای ماندگار می‌سازد و شناسهٔ آن را برمی‌گرداند. جریان پیشرفتِ احرازهویت‌شده امکان اتصال دوباره دارد. لغو، درخواست توقف است نه اثبات توقف کار راه دور. صفحه‌بندی، سقف payload، ثبت تکرارپذیر فرمان و خطای ساخت‌یافته تعریف شوند. timeout مرورگر کار را حذف نمی‌کند.

ورودی هشدار باید schema معتبر، فرستندهٔ دارای دامنه، کنترل بازپخش و تکرار و سقف نرخ داشته باشد. دادهٔ خراب به بازبینی دستی برود. ورودی ناشناس حق اجرای عملیات دلخواه ندارد و مرورگر نیز به مدل یا اتصال‌دهنده مسیر مستقیم نخواهد داشت.
