# سرور مستقل Zabbix و پاسخ‌گویی هوش مصنوعی محلی بر اساس وضعیت آن

[English](../en/ZABBIX_SERVER.md) · [راهنمای شروع](START_HERE.md) · [فهرست](INDEX.md) · [رکورد تخصیص](../requirements/ZABBIX_SERVER_PLAN.json)

**به‌روزرسانی: ۲۰ سپتامبر ۲۰۲۶. وضعیت: طرح پیشنهادی استقرار؛ نه ماشین ساخته‌شده یا سامانهٔ آزموده‌شده.** مالک خواسته است پیشنهاد سرور مستقل Zabbix در مخزن ثبت شود. برای مسیر ایجاد سرور پایش جدید، این طرح جایگزین پیشنهاد قبلیِ `zabbix-lab` کوچک می‌شود؛ اما مجوز نصب دوبارهٔ Zabbix موجود یا تغییر ESXi نیست.

## ۱. یک ماشین پایش، جدا از سه ماشین NextOps

یک ماشین `zabbix-server` روی همان G10 در نظر بگیرید. Zabbix به‌طور پیوسته داده‌های پایش را جمع می‌کند. هر زمان کاربر مجاز سؤال کند، اتصال‌دهندهٔ NextOps شواهد مرتبط را از API می‌خواند و مدل محلی روی CPU آن‌ها را توضیح می‌دهد. نصب Zabbix به‌تنهایی اتصال‌دهنده و مسیر پاسخ‌گویی NextOps را پیاده‌سازی نمی‌کند.

| تنظیم | پیشنهاد اولیه |
|---|---|
| نام ماشین | `zabbix-server` |
| سیستم‌عامل مهمان | Ubuntu Server 24.04 LTS، پس از بررسی سازگاری |
| پردازنده | ۴ vCPU |
| توپولوژی CPU | حالت خودکارِ پشتیبانی‌شده در اولویت؛ جایگزین دستی: ۴ هسته در هر سوکت و یک سوکت مجازی |
| CPU Hot Add | برای چیدمان ثابت اولیه خاموش بماند |
| حافظه | ۱۶ GiB |
| مجموع دیسک مجازی | ۲۰۰ GiB؛ شامل سیستم‌عامل، پایگاه داده و swap مهمان |
| محل ذخیره | DS-C؛ نام مستعار بزرگ‌ترین datastore در رکورد پالایش‌شده |
| میان‌افزار نصب جدید | UEFI |
| شبکه | مسیر داخلی مجاز، نشانی خصوصی ثابت، نام‌گشایی محلی و HTTPS معتبر |
| GPU | ندارد |

این منابع، بودجهٔ شروع‌اند؛ نه رزرو اعمال‌شده، حداقل اندازه‌گیری‌شده یا تضمین ظرفیت برای تعداد مشخصی تجهیز. Zabbix در یکی از نمونه‌های ظرفیت متوسط، چهار پردازنده و ۱۶ GiB حافظه پیشنهاد کرده، اما ارزیابی متناسب با بار واقعی را ضروری دانسته است [1]. دیسک ۲۰۰ GiB پیشنهاد مهندسی این پروژه است. تعداد شاخص‌ها، فاصلهٔ نمونه‌برداری، نوع داده، رشد پایگاه و دورهٔ نگهداری تعیین‌کننده‌اند.

برای توپولوژی خودکار، سطح سازگاری ماشین و مقدار ذخیره‌شده را طبق [یادداشت ESXi](ESXI_BASELINE.md) بررسی کنید. یک سوکت مجازی چهارهسته‌ای به معنای رزرو سوکت فیزیکی یا اثبات جای‌گذاری NUMA نیست.

در این چیدمان **سه ماشین NextOps و یک ماشین Zabbix، در مجموع چهار ماشین** داریم. ماشین آزمایشگاهی قبلی با ۴ vCPU، حافظهٔ ۸ GiB و دیسک ۱۰۰ GiB را هم‌زمان اضافه نکنید. اگر Zabbix محلیِ مناسب و مجاز از قبل وجود دارد، ابتدا همان را بررسی و استفاده کنید؛ آن را بی‌دلیل تکرار یا قالب‌بندی نکنید. این راهنما مسیر ایجاد سرور جدید را توضیح می‌دهد.

## ۲. نرم‌افزارهای پیشنهادی داخل zabbix-server

| جزء | پیشنهاد |
|---|---|
| پایش | Zabbix 7.0 LTS با نسخهٔ نگهداری‌شده و بازبینی‌شدهٔ شاخهٔ 7.0 [2] |
| پایگاه داده | PostgreSQL 16 با به‌روزرسانی نگهداریِ بازبینی‌شده [1] |
| رابط وب و API | رابط Zabbix، Nginx و PHP-FPM سازگار [1] |
| پایش مهمان | Zabbix Agent 2 |
| مدیریت سرویس | بسته‌های بومی سیستم‌عامل و systemd |

نسخهٔ دقیق، منبع بسته، checksum و قالب‌های سازگار در زمان آماده‌سازی تثبیت شوند. این جدول فایل قفل وابستگی یا گزارش نصب نیست. ارتقای نسخهٔ اصلی، TimescaleDB، ماشین جدا برای پایگاه Zabbix، مجموعه‌ای از proxyها یا محیط AI اضافی شرط اولین خروجی نیستند.

نمونهٔ PostgreSQL در این ماشین فقط متعلق به Zabbix است. پایگاه مستقل NextOps ابتدا داخل `nextops-app` قرار می‌گیرد و سپس طبق نقشهٔ راه به `nextops-db` منتقل می‌شود. حساب نامحدود، رمز، schema یا سرویس مشترک پایگاه بین این دو محصول ایجاد نکنید. مدل و اتصال‌دهنده به اطلاعات ورود هیچ‌یک از پایگاه‌ها دسترسی ندارند.

## ۳. چیدمان LVM برای دیسک ۲۰۰ GiB

**فقط برای دیسک خالیِ مهمان جدید.** دستور قالب‌بندی در پوستهٔ ESXi اجرا نشود و ماشین دارای داده دوباره فرمت نشود. ردیف‌های زیر همان ۲۰۰ GiB را تقسیم می‌کنند؛ دیسک اضافه نیستند. نام گروه حجم `vg_zabbix` باشد.

| پارتیشن یا حجم منطقی | اندازه GiB | نوع | محل اتصال | کاربرد |
|---|---:|---|---|---|
| EFI System Partition | ۱ | FAT32 / ESP، بیرون LVM | `/boot/efi` | فایل‌های راه‌اندازی UEFI |
| پارتیشن boot | ۲ | ext4، بیرون LVM | `/boot` | کرنل و فایل‌های راه‌اندازی |
| `vg_zabbix/lv_root` | ۳۲ | ext4 | `/` | سیستم‌عامل و نرم‌افزارها |
| `vg_zabbix/lv_var` | ۱۶ | ext4 | `/var` | دادهٔ متغیر سیستم و حافظهٔ نهان بسته‌ها |
| `vg_zabbix/lv_log` | ۸ | ext4 | `/var/log` | گزارش سیستم و سرویس‌ها |
| `vg_zabbix/lv_pg` | ۱۱۲ | ext4 | `/var/lib/postgresql` | داده، ایندکس و WAL پایگاه |
| `vg_zabbix/lv_swap` | ۴ | Linux swap | بدون مسیر پوشه | swap مهمان |
| فضای تخصیص‌نیافته در VG | حدود ۲۵ | فایل‌سیستم نیست | ندارد | افزایش حجم موردنیاز در آینده |
| **مجموع دیسک** | **۲۰۰** | | | |

پس از EFI و `/boot`، پارتیشن باقی‌مانده را به PV تبدیل کنید و `vg_zabbix` و حجم‌های عادی LVM را در آن بسازید. حجم منطقی با نام «free» لازم نیست؛ بخشی از VG واقعاً بدون تخصیص بماند. هم‌ترازی و فراداده باعث می‌شوند مقدار آزاد نهایی کمی کمتر از ۲۵ GiB باشد؛ مقدار واقعی نصب‌کننده را مبنا بگیرید.

پیش از ایجاد پایگاه PostgreSQL، فایل‌سیستم `/var/lib/postgresql` باید درست متصل و بررسی شده باشد. سهم ۱۱۲ GiB آن مستقل از سهم ۱۶ GiB مسیر `/var` است، هرچند نام مسیر تو‌در‌تو است. راه‌اندازی پایگاه باید به وجود mount درست وابسته باشد؛ نبود آن نباید باعث نوشتن بی‌سروصدا در پوشهٔ زیرین روی ریشه شود. مالکیت محدود، پشتیبان و چرخش لاگ را پیش از ورود داده آماده کنید. مستندات نصب‌کنندهٔ Ubuntu، پارتیشن‌بندی سفارشی، VG و LV را توضیح می‌دهد [3].

EFI موجود و مناسب را دوباره نسازید. برای مهمان نصب‌شده با BIOS قدیمی، بدون طرح بازبینی‌شده میان‌افزار را تغییر ندهید. رمزگذاری به مسیر بازکردن قفل و بازیابیِ مستقل از اینترنت نیاز دارد؛ شروع خودکار را پیش از آزمون تضمین نکنید. swap مهمان داخل همین دیسک است؛ swap ماشین در ESXi جدا حساب می‌شود.

## ۴. نگهداری داده و کنترل رشد

**پیشنهاد شروع:** هفت روز history با جزئیات و نود روز trends برای شاخص‌های عددی، با استثناهای صریح و مصوب برای شاخص‌های مهم رخداد. تنظیم مؤثر هر item، قالب و housekeeping بررسی شود؛ نصب Zabbix این مقادیر را خودکار اعمال نمی‌کند.

History مقادیر جمع‌آوری‌شده را نگه می‌دارد؛ trends خلاصهٔ ساعتی دادهٔ عددی است [4]. پس از حذف history، روند قدیمی جایگزین تک‌تک نمونه‌ها یا خط زمانی دقیق رخداد نیست. پاسخ باید دقت زمانی و مرز نگهداری واقعی را نشان دهد. تاریخچهٔ حجیم در Zabbix بماند و کامل در NextOps کپی نشود.

پیش از گسترش دامنه، رشد داده و ایندکس و WAL، تأخیر نوشتن، صف، شاخص‌های نامعتبر و فضای آزاد سنجیده شوند. فاصلهٔ نمونه‌برداری و ورود لاگ بازبینی شود؛ ۱۱۲ GiB پایگاه، ظرفیت تضمین‌شدهٔ محیط نامعلوم نیست. فضای آزاد VG برای افزایش بازبینی‌شده است، نه پشتیبان یا اثبات بازگشت فضا به datastore. هشدار کمبود فضا محلی باشد و حذف خودکارِ تنها مدل سالم یا دادهٔ الزامی پایگاه راه‌حل محسوب نشود.

## ۵. قرارداد سؤال تا پاسخ فقط‌خواندنی

کاربر در `nextops-app` احراز هویت می‌شود و دامنهٔ درخواست بررسی و ثبت می‌گردد. برنامه درخواست نام‌گذاری‌شده و محدود را به `nextops-connectors-ro` می‌فرستد. فقط اتصال‌دهندهٔ Zabbix، API مجاز را با HTTPS فراخوانی می‌کند. برنامه شواهد را اعتبارسنجی و شمارش را با کد قطعی انجام می‌دهد؛ سپس متن پالایش‌شده و بدون رمز به `nextops-ai` می‌رود. پاسخ همراه منبع، زمان، تازگی، موارد نامعلوم و ممیزی برمی‌گردد.

API از نوع JSON-RPC و در مسیر `api_jsonrpc.php` رابط نصب‌شده است؛ ارتباط HTTPS باید گواهی معتبر داشته باشد [5]. مسیر پایهٔ واقعی شناسایی شود و `/zabbix` برای همهٔ نصب‌ها فرض نشود. HTML داشبورد را نخراشید، SQL آزاد ندهید و برای هر سؤال با SSH به سرور وارد نشوید.

هویتی اختصاصی مانند `nextops-reader` فقط به گروه‌های میزبان مصوب و منابع فقط‌خواندنی دسترسی داشته باشد. نقش سفارشی با فهرست صریح و غیرخالی روش‌های مجاز API تنظیم شود [6]. توکن مجوزهای کاربر خودش را به ارث می‌برد [7]؛ داشتن توکن به‌تنهایی فقط‌خواندنی بودن را تضمین نمی‌کند. محدودیت روش و دامنه هم در Zabbix و هم مستقل در درگاه آزموده شود.

از روش‌های سازگار `host.get`، `hostinterface.get`، `problem.get`، `trigger.get` و `item.get` شروع کنید. `apiinfo.version` فقط شناسایی نسخه است، نه شاهد موفقیت خواندنِ احرازهویت‌شده. `history.get` و `event.get` فقط در صورت نیاز و با دامنهٔ محدود مجاز باشند. تأیید یا بستن مشکل، اجرای اسکریپت راه دور، تغییر تنظیمات و همهٔ روش‌های خارج از فهرست رد شوند. ساختار ورودی، مقصد، فیلد، بازهٔ زمانی، سقف ردیف و بایت و مهلت اجرا محدود باشند؛ مدل حق انتخاب آزاد روش API ندارد.

توکن فقط از مسیر امن به فرایند جداشدهٔ اتصال Zabbix برسد. مرورگر، پرامپت، Git، تصویر، لاگ عادی یا محیط مشترکِ نامحدود محل نگهداری آن نیستند. انقضا، تعویض و بازیابی محلی محافظت شوند؛ نبود اعتبار به خطای روشن برسد، نه هویت جایگزین.

شمارش با کد قطعی و دامنهٔ مجاز انجام شود. مشکل حل‌شده و فعال، نگهداری و تعلیق هشدار و نتیجهٔ کامل یا ناقص جدا باشند. مشکل قدیمیِ حل‌نشده را از شمارش همهٔ مشکلات جاری حذف نکنید. پاسخ تازهٔ API ممکن است شامل اندازه‌گیری قدیمی باشد؛ زمان فراخوانی و زمان اندازه‌گیری هر دو حفظ شوند. وضعیت زنده از حافظهٔ مدل ساخته نشود.

## ۶. خودپایشی Zabbix و مرزهای شبکه

قالب سلامت سرورِ متناسب با نسخه و پایش مناسب مهمان را تنظیم کنید. مرجع رسمی، شاخص‌های داخلی فرایند، cache، صف و uptime را معرفی می‌کند [8]. دادهٔ غایب یا قدیمی یعنی سلامت موتور نامعلوم است، نه سالم. سه موضوع جدا گزارش شوند:

| بُعد وضعیت | شاهد |
|---|---|
| دسترسی API | نتیجهٔ واقعی فراخوانی احرازهویت‌شده |
| تجهیزات تحت پایش | میزبان‌ها، مشکلات جاری و اندازه‌گیری‌ها در دامنهٔ مجاز |
| موتور پایش | شاخص‌های تازهٔ خودپایشی، صف، cache، فرایند و کمبود داده |

در آغاز، خود `zabbix-server` و سه مهمان Ubuntu مربوط به NextOps از مسیر پایش بازبینی‌شده بررسی شوند. این آماده‌سازی کار مسئول زیرساخت است، نه اجازهٔ تغییر برای AI. هویت عامل پایش سیستم‌عامل از سرویس مدل جدا باشد و فقط ترافیک و بررسی ضروری مجاز شود. برای آسان کردن پایش، به مدل مسیر شبکهٔ تجهیزات یا اطلاعات ورود ندهید. اجرای فرمان آزاد ممنوع باشد؛ پورت مدیریت عمومی و مسیر مستقیم مرورگر به مدل ایجاد نشود.

مدل از Zabbix جدا می‌ماند و فقط اتصال‌دهنده فراخوانی API را آغاز می‌کند. مجوز API با پایگاه داده یکی نیست. PostgreSQL داخل VM زبیکس بماند و endpoint عمومی برای NextOps نباشد.

## ۷. زمان ساخت و معیار پذیرش

ترتیب ماشین‌های NextOps حفظ می‌شود: برنامه، AI و اتصال فقط‌خواندنی. `zabbix-server` را در همان نوبت کاریِ دارای مجوز یا هم‌زمان با 1A و 1B آماده کنید؛ اما **پایش و API محدود آن باید پیش از اتصال زندهٔ گام 1C آماده باشند**. ساخت VM مجوز دسترسی به تجهیز عملیاتی نیست.

گام‌ها همچنان 1A هویت و سیاست و وضعیت ماندگار و ممیزی، 1B پاسخ CPU واقعی، 1C شواهد واقعی فقط‌خواندنی، 1D پاسخ کامل دارای منبع و 1E پذیرش آفلاین هستند. پاسخ عمومی مدل یا داشبورد سالم زبیکس به‌تنهایی پایان مرحلهٔ یک نیست.

| بررسی | شاهد پذیرش؛ همه فعلاً اجرا نشده‌اند |
|---|---|
| آمادگی سرور | mount درست پایگاه، سرویس‌ها، ورود محلی، شاخص‌ها و خواندن API محدود |
| صحت شواهد | مطابقت شمارش با API و تفکیک سلامت موتور، تجهیزات و دسترسی API |
| کنترل دسترسی | رد خواندن خارج از دامنه و همهٔ تغییرات؛ آزمون توکن و متن مخرب رخداد |
| پاسخ آفلاین | پاسخ تازهٔ فارسی و انگلیسی با اینترنت سرور و مرورگر قطع و شبکهٔ داخلی مجاز برقرار |
| شروع آفلاین | ورود تازه و شروع سرد Zabbix، پایگاه، اتصال، برنامه و مدل از فایل‌های محلی ماندگار |
| خطا | گزارش صادقانهٔ قطع Zabbix، انقضای توکن و دادهٔ غایب یا قدیمی؛ ادامهٔ سؤال عمومی محلی |
| بازیابی و ظرفیت | آزمون مجاز بازیابی آفلاین و کمبود فضا و اندازه‌گیری منابع و تأخیر؛ نه پرکردن عمدی datastore عملیاتی |

این بررسی‌ها مکمل ZBX-01 تا ZBX-08 و موارد قابل‌اعمال OFF-01 تا OFF-10 هستند، نه جایگزین آن‌ها. سؤال نمونه: «آیا زبیکس داده‌ها را درست جمع می‌کند؟ چه مشکلات فعالی داریم و کدام اندازه‌گیری‌ها قدیمی‌اند؟» معادل انگلیسی نیز آزموده شود. نمونه‌برداری Zabbix مستقل از گفت‌وگو ادامه دارد و دستیار هنگام سؤال شواهد را می‌خواند.

ردیف‌ها چیدمان جایگزین‌اند، نه جمع‌شونده یا سقف همهٔ سربارها. مرحلهٔ هشتِ فقط‌خواندنی می‌تواند ردیف میانی را نگه دارد. ماشین آزمایشگاهی قبلی را اضافه نکنید و VM موجود را دوباره از فضای آزاد کم نکنید. سرویس PostgreSQL زبیکس ماشین جدا نیست.

با فرض فضای آزاد قبلی DS-C برابر 3166.8701171875 GiB و مصرف موجودِ ثابت، چیدمان اول پیش از سربار و رشد بیشتر **۲۰۰۲٫۸۷ GiB آزاد** باقی می‌گذارد؛ یعنی **۱۱۰۸٫۶۸ GiB بالاتر از حاشیهٔ دقیق 894.1875 GiB**. برای دو چیدمان بعدی، فضای آزاد فرضی ۱۶۳۸٫۸۷ و ۱۵۴۲٫۸۷ GiB است. این محاسبه رزرو فضا یا تأیید کارایی نیست.

سقف سه‌ترابایتی پروژه و حدود ۹۰۰ GiB فضای آزاد هدف روی DS-C حفظ شوند. رشد thin موجود، فایل VMX، محل واقعی swap، snapshot و ادغام، فایل ورودی و نسخهٔ بازیابی جدا حساب شوند. swap لینوکس داخل VMDK است. برای جا شدن اعداد، دیسک موجود کوچک یا رزرو حافظه تغییر نکند. همهٔ [شروط ذخیره‌سازی](../STORAGE_PLAN.md) برقرارند؛ این راهنما فقط اعداد چیدمان شامل Zabbix را به‌روز می‌کند.

چهار ماشین اولیه یک نقطهٔ خرابی فیزیکی دارند. قطع Zabbix نباید سلامت تجهیزات گزارش شود؛ خرابی G10 می‌تواند هر دو سامانه را از کار بیندازد. پیش از بهره‌برداری، پشتیبان مستقلِ داخلی یا رسانهٔ آفلاین و در صورت نیاز بررسی مستقل قطعی میزبان لازم است. VM یا datastore دیگر روی همین G10، بازیابی پس از ازدست‌رفتن میزبان نیست.

## ۹. دامنهٔ تغییر و تقدم منابع

این مشخصات طرح‌اند، نه زیرساخت مشاهده‌شده. فقط پیشنهاد قبلی آزمایشگاهِ Zabbix جدید و مجموع‌های وابسته به آن در راهنمای شروع، برنامهٔ سرورها، مثال ذخیره‌سازی و بخش ۱۸ پرامپت ۳.۰ جایگزین می‌شوند. تعداد سه، چهار و پنج برای **ماشین‌های خود NextOps** همچنان درست است. یازده اتصال اولیه، معیارهای امنیت، CPU محلی و نیازهای بایگانی حفظ شده‌اند. [اصلاحیهٔ استقرار](../requirements/DEPLOYMENT_UPDATE.md) را ببینید.

اعداد منابع، LVM و نگهداری از پیشنهاد قبلی آمده‌اند و انتخاب مهندسی‌اند. منابع رسمی فقط رفتار نرم‌افزار را تأیید می‌کنند، نه ظرفیت این G10. منابع در ۲۰ سپتامبر ۲۰۲۶ بررسی شدند؛ نسخهٔ دقیق نصب به فایل قفل و بستهٔ آفلاین بازبینی‌شده نیاز دارد. برای این تغییر هیچ میزبان، مدل، API زبیکس، قالب‌بندی دیسک یا آزمون آفلاینی اجرا نشده است.
