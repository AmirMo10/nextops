# چک‌لیست شروع سرورها

**وضعیت: تحویل به مسئول اجرا است، نه مجوز ساخت.** مرحلهٔ صفر و source فعلی 1A/1B، از جمله
scriptهای محافظت‌شدهٔ لایهٔ package، تأیید شده‌اند. ساخت ماشین، نصب سیستم‌عامل، تغییر شبکه
و فایروال، اجرای package، دسترسی مقصد، راه‌اندازی مجدد و کار تخریبی دیسک همچنان به مجوز
تغییر جدا و ثبت‌شده نیاز دارند.

## نخست چه کاری انجام شود؟

کار را با **پیش‌بررسی خصوصی استقرار برای `nextops-app`** آغاز کنید. هنوز محصول NextOps را
روی سرور نصب نکنید: مخزن پایهٔ برنامه و scriptهای محافظت‌شدهٔ OS-package را دارد، اما
bundle package مصوب هر role، release آفلاین برنامه، unitهای تولید، تنظیم reverse proxy،
روش آزمودهٔ backup/restore و قفل نهایی نسخهٔ پایگاه تولید هنوز آماده نیستند.

در همان بازهٔ برنامه‌ریزی مصوب، اطلاعات هر چهار ماشین را آماده کنید. پس از مجوز جداگانهٔ
ساخت، ترتیب ایجاد چنین است:

| ترتیب | سرور | vCPU | حافظه | دیسک | کاربرد آغازین |
|---:|---|---:|---:|---:|---|
| ۱ | `nextops-app` | ۸ | ۳۲ GiB | ۲۰۰ GiB | API، worker ماندگار، ممیزی و PostgreSQL اولیهٔ NextOps |
| ۲ | `nextops-ai` | ۲۴ | ۱۲۸ GiB | ۵۰۰ GiB | استنتاج محلی فقط روی CPU |
| ۳ | `nextops-connectors-ro` | ۴ | ۸ GiB | ۸۰ GiB | gateway و runnerهای جدا و فقط‌خواندنی |
| پیش‌نیاز موازی پیش از 1C | `zabbix-server` | ۴ | ۱۶ GiB | ۲۰۰ GiB | پایگاه پایش، server، رابط/API و Agent 2 |

محل پیشنهادی هر چهار ماشین DS-C است. جمع ۴۰ vCPU، حافظهٔ ۱۸۴ GiB و دیسک مجازی ۹۸۰ GiB
است. این عدد بودجه است، نه رزرو. هر ماشین موجود را پیش از کم‌کردن ظرفیت تطبیق دهید.

## ۱. رکورد خصوصی تغییر را باز کنید

یک رکورد خارج از Git با شناسهٔ تغییر بسازید. کلیدهای `required_inputs` هر فایل در
`deploy/server-dependencies/` را در همان رکورد حل کنید. دست‌کم این موارد خصوصی ثبت شوند:

- تأییدکننده، مجری، عملیات مجاز، بازهٔ نگه‌داری، شرط توقف و مسئول rollback؛
- نام واقعی ماشین، نگاشت datastore، نشانی و DNS، VLAN و مبدا فایروال، مسیر مدیریت و
  کنسول بازیابی و کلید میزبان SSH؛
- image و checksum دقیق Ubuntu، سازگاری سخت‌افزار VM، firmware، تصمیم Secure Boot،
  controller شبکه/دیسک، thin/thick و چیدمان دیسک مهمان؛
- CPU/RAM آزاد، reservation و contention، فضای تازهٔ DS-C، تعهد thin، نیاز snapshot و
  consolidation، محل swap در ESXi و سلامت storage؛
- DNS و زمان و PKI محلی، تمدید/ابطال گواهی، منبع بسته، مقصد backup، فضای restore، RPO/RTO
  و مسیر پایش؛
- فقط شناسهٔ مرجع secret. رمز، token، کلید خصوصی، secret بازیابی، نشانی واقعی، UUID
  datastore یا route را در مخزن یا پرامپت مدل قرار ندهید.

پس از تخصیص مصوب و همهٔ سربارها حدود ۹۰۰ GiB فضای آزاد در DS-C حفظ شود. VMX، snapshot،
فضای staging و restore، رشد موجود و swap ماشین خاموش جدا حساب شوند. در این چک‌لیست shrink،
delete، migrate، repartition یا تغییر reservation حافظه انجام ندهید.

## ۲. پیش از ساخت VM دروازهٔ میزبان را بگذرانید

فقط از رابط مدیریتی/ESXi مجاز و فقط‌خواندنی تأیید کنید:

1. ماشین موردنظر با نام یا رکورد دیگری از قبل وجود ندارد.
2. شاهد CPU، حافظه، datastore، سلامت storage و تعهدهای باز برای بازهٔ تغییر تازه است.
3. سطح سازگاری VM و CPU مهمان با ESXi 8.0.3 فعلی سازگار است و خود ESXi تغییر نمی‌کند.
4. مدیریت، کنسول بازیابی، DNS/زمان محلی و backup مستقل بدون اینترنت عمومی کار می‌کنند.
5. قواعد شبکه فقط جریان‌های پروندهٔ همان سرور را می‌دهند. برنامه و مدل دسترسی مستقیم به
   شبکهٔ مدیریت مقصد ندارند؛ فقط مرز connector ممکن است بعداً route و credential محدود بگیرد.

اگر شاهد قدیمی است، ماشین موجود تطبیق نمی‌شود، سلامت storage نامعلوم است، حاشیهٔ DS-C
نقض می‌شود یا مسیر rollback/recovery وجود ندارد، توقف کنید.

## ۳. پس از مجوز جداگانهٔ ساخت

در هر مهمان تازهٔ Ubuntu این بررسی‌های فقط‌خواندنی را در رکورد خصوصی ذخیره کنید:

```bash
cat /etc/os-release
uname -r
systemd-detect-virt
lscpu
free -h
lsblk -o NAME,TYPE,SIZE,FSTYPE,MOUNTPOINTS,ROTA
findmnt
df -hT
timedatectl status
sudo ss -lntup
```

انتظار می‌رود image مصوب Ubuntu، مجازی‌سازی VMware، مقدار درست CPU/RAM/disk، فقط دیسک و
mountهای بررسی‌شده، زمان محلی معتبر و نبود listener یا تداخل port نامعلوم ثبت شود. خروجی
کامل خصوصی بماند، چون ممکن است شناسهٔ زیرساخت داشته باشد.

## ۴. پیش از هر اجرای package، bundle را اعتبارسنجی کنید

bundle دقیق، احرازشده و آفلاینِ role سرور را بیرون از Git آماده و از
[راهنمای مجری installer](../../deploy/installers/README.md) پیروی کنید. برای نخستین سرور app،
کل bundle را بدون تغییر package یا service بررسی کنید:

</div>

```bash
./deploy/installers/install-nextops-app.sh --check \
  --bundle-dir /srv/nextops-bundles/nextops-app \
  --bundle-manifest-sha256 "$APP_BUNDLE_MANIFEST_SHA256"
```

<div dir="rtl">

روی نقش‌های دیگر به‌ترتیب از `install-nextops-ai.sh`، `install-nextops-connectors-ro.sh`
یا `install-zabbix-server.sh` استفاده کنید. اگر lock دقیق package، hash جداگانه و تأییدشدهٔ
manifest یا repository محلی امضاشده غایب است، validation را متوقف کنید. `--apply` فقط پس از
مجوز جداگانهٔ نصب package، preflight موفق Ubuntu 24.04/VMware، مالکیت root و جلوگیری از
نوشتن دیگران در bundle و همراه نشان مجوز و change ID لازم در راهنمای مجری اجرا شود. این
scriptها فقط بسته‌های دقیق Ubuntu را نصب می‌کنند؛ پایگاه را initialize نمی‌کنند، سرویس را
تنظیم یا start نمی‌کنند، NextOps را deploy نمی‌کنند، مدل وارد نمی‌کنند و آماده بودن سرور را
ثابت نمی‌کنند.

سپس این توقف‌های مخصوص هر سرور را رعایت کنید:

- **`nextops-app`:** فعلاً مهمان را رزرو و فقط شاهد سیستم‌عامل، شبکه و storage را کامل
  کنید. تا زمانی که release برنامه، نسخهٔ پایگاه، roleهای login، unit سرویس، backup و روش
  downgrade/recovery با هم ارتقا نیافته‌اند، پایگاه NextOps را initialize و migration را اجرا
  نکنید. CI اکنون jobهای جدا با image ثابت برای PostgreSQL 16.15 و 17.6 تعریف می‌کند تا نسخهٔ
  مستقر و نسخهٔ آیندهٔ موردنظر مستقل آزموده شوند.
- **`nextops-ai`:** پیش از انتخاب build مربوط به CPU، flagهای واقعی CPU و نمای NUMA مهمان
  را ثبت کنید. مدل دانلود نکنید و CUDA، ROCm، container گرافیکی یا fallback راه دور نصب
  نکنید. checksum و مجوز مدل/runtime، بودجهٔ حافظه و کیفیت/زمان پاسخ سنجیده هنوز شرط‌اند.
- **`nextops-connectors-ro`:** route و credential مقصد وجود نداشته باشند. تأیید کنید VM در
  حالت پیش‌فرض به مقصدهای مدیریتی دسترسی ندارد. دسترسی بعدی فقط با شناسهٔ ثابت مقصد،
  allowlist روش، credential محافظت‌شدهٔ هر runner و آزمون صریح فقط‌خواندنی است.
- **`zabbix-server`:** می‌تواند موازی آماده شود تا پیش از 1C حاضر باشد، اما ابتدا اگر
  Zabbix محلی مناسب و مجاز وجود دارد بررسی و همان استفاده شود. برای دیسک تازه و خالی از
  راهنمای ویژهٔ Zabbix پیروی و mountهای LVM پیش از ساخت پایگاه تأیید شوند. فرمان دیسک آن
  راهنما هرگز روی دیسک شناسایی‌شده یا غیرخالی اجرا نشود.

## ۵. ماشین روشن را «آماده» ننامید

سرور فقط زمانی از *prepared* به *ready* می‌رود که دروازه‌های پذیرش پرونده‌اش شاهد داشته
باشند. برای `nextops-app` در ادامه شامل artifact آفلاین معتبر، role محدود پایگاه،
upgrade/downgrade و restore جدا، bootstrap/recovery هویت، API احرازشده، رفتار خرابی audit،
بازیابی restart، TLS، backup و کار با اینترنت بسته است. کد فعلی و CI به‌تنهایی مجوز این
عملیات روی سرور را نمی‌دهند.

خلاصهٔ پاک‌سازی‌شده شامل شناسهٔ تغییر، زمان، منابع واقعی، OS/kernel، تأیید mount، دسترسی
وابستگی محلی، وضعیت backup/restore، نتیجهٔ هر پذیرش، انحراف و نتیجهٔ rollback برگردانده شود.
خروجی خام زیرساخت و همهٔ secretها فقط در سامانهٔ خصوصی مصوب نگه‌داری شوند.

منبع اصلی هر ماشین فایل YAML آن و [راهنمای پرونده‌های استقرار](DEPLOYMENT_DOSSIERS.md)
است. برنامهٔ دیسک و سرویس پایش در [راهنمای Zabbix](ZABBIX_SERVER.md) آمده است.
