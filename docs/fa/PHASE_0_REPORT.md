# گزارش مرحلهٔ صفر: معماری، فاصله‌ها و آمادگی

[English](../en/PHASE_0_REPORT.md) · [شروع کار](START_HERE.md) · [وضعیت پروژه](../PROJECT_STATE.md) · [کار بعدی](../NEXT_TASK.md) · [مدل تهدید](../requirements/nextops-threat-model.md)

وضعیت: پیشنهاد برای تأیید مالک. تاریخ: ۲۰ سپتامبر ۲۰۲۶. دامنه: فقط بازبینی مخزن و شواهد ارسالی. هیچ VM، بسته، مدل، شبکه، Zabbix، ESXi، دیسک، راه‌اندازی مجدد یا محیط عملیاتی تغییر نکرده است.

## ۱. پیشنهاد اصلی معماری

معماری پیشنهادی، هستهٔ مدیریتی ماژولار روی چهار VM در ESXi موجود است: سه ماشین NextOps و یک ماشین مستقل Zabbix. در شروع، PostgreSQL مرجع NextOps به‌صورت سرویس محدود داخل `nextops-app` قرار می‌گیرد؛ مدل CPU محلی در `nextops-ai` و مرز اتصال فقط‌خواندنی در `nextops-connectors-ro` جدا می‌مانند.

مالک این فرض‌های مرحلهٔ صفر را تأیید کرده است:

- فعلاً یک سازمان داریم؛ پشتیبانی چندسازمانی بعداً با طراحی و مهاجرت جدا اضافه می‌شود.
- مقیاس اولیه کوچک است؛ رشد بعدی باید بر پایهٔ اندازه‌گیری و قراردادهای دارای نوع انجام شود.
- مسیر منتخب، ساخت `zabbix-server` مستقل است، نه آزمایشگاه کوچک قدیمی.
- این گزارش دسترسی کاربر از LAN یا VPN داخلی را فرض می‌کند؛ ورودی عمومی اینترنت مجاز نشده است.

اولین نتیجهٔ کامل، پاسخ تازهٔ فارسی یا انگلیسی به سؤال وضعیت Zabbix با شواهد واقعی و مجاز، مدل CPU محلی، اینترنت مسدود، نمایش منبع و زمان و دامنه و ثبت ممیزی است. پس از تأیید معماری و مجوز جداگانه، ترتیب اجرا `nextops-app`، سپس `nextops-ai` و سپس `nextops-connectors-ro` است. Zabbix می‌تواند کنار 1A و 1B آماده شود، ولی پیش از خواندن زندهٔ 1C باید آماده باشد.

## ۳. واقعیت‌های سخت‌افزار و مجهول‌های باقی‌مانده

واقعیت‌های زیر از خروجی ارسالی مالک در `HARDWARE_BASELINE.json` هستند، نه اتصال مستقیم این بازبینی:

| واقعیت | وضعیت شاهد |
|---|---|
| VMware ESXi 8.0.3، build 24414501، Update 3، Patch خام 55 | ارسالی مالک؛ نگاشت مرجع به U3c |
| ۴ بسته، ۱۱۲ هستهٔ فیزیکی، ۲۲۴ رشته و Hyperthreading فعال | جمع ارسالی |
| ۴ گرهٔ NUMA | جمع ارسالی |
| ۱٬۴۴۲٬۷۴۳٬۶۳۱٬۸۷۲ بایت، حدود ۱۳۴۳٫۶۶ GiB حافظه | بایت ارسالی و تبدیل حسابی |
| شناسهٔ 6/85/7 برای CPU 0 و بخشی از CPU 1 | نمونهٔ ناقص؛ نه مدل تجاری دقیق |
| DS-C با ۳۵۷۶٫۷۵ GiB کل و ۳۱۶۶٫۸۷ GiB آزاد | مشاهدهٔ لحظه‌ای ارسالی |
| نبود GPU و اجرای همهٔ AI روی CPU محلی | الزام مالک، نه نتیجهٔ موجودی دستگاه |

پیش از ساخت هنوز لازم است: منابع آزاد و بار و reservation، نگاشت واقعی NUMA، نسخهٔ سخت‌افزار VM و ISA مهمان، تعهد thin و محل swap و سلامت/تأخیر دیسک، شبکه و DNS/زمان/TLS و مسیر بازیابی، نسخه و دامنهٔ Zabbix، فایل‌های آفلاین، مقصد پشتیبان بیرون میزبان و هدف عددی کیفیت/تأخیر/RPO/RTO.

Ubuntu Server 24.04 LTS فقط مهمان پیشنهادی است و جایگزینی ESXi یا سازگاری را ثابت نمی‌کند. مشاهدهٔ میزبان با فرمان‌های Linux مهمان مخلوط نشود.

الگوی خصوصی و فقط‌خواندنی کشف میزبان:

```sh
#!/bin/sh
set -eu
esxcli system version get
esxcli hardware cpu global get
esxcli hardware memory get
esxcli hardware cpu list
esxcli storage filesystem list
esxcli system stats uptime get
```

خروجی خام دارای نام VM، IP، UUID، شمارهٔ سریال، مسیر یا نام واقعی datastore و اطلاعات ورود نباید در مخزن عمومی منتشر شود.

## ۴. ردیابی مشخصات اولیه و اصلاحات صریح

هر ۵۱ بخش اولیه و یازده خانوادهٔ اتصال در `TRACEABILITY.md` باقی‌اند. اصلاحات حاکم عبارت‌اند از: امنیت و ممیزی پیش از دسترسی واقعی؛ پایان مرحلهٔ یک با پاسخ Zabbix آفلاین؛ AI صرفاً CPU محلی؛ جایگزینی اعداد قدیمی با شواهد جدید ESXi؛ PostgreSQL به‌عنوان مرجع اولیه؛ نبود میان‌بُر مدیر؛ نبود ادعای HA تک‌میزبان؛ و جایگزینی Zabbix مستقل با آزمایشگاه کوچک قدیمی در مسیر منتخب.

گزارش مرحلهٔ صفر می‌تواند با مجهول‌های صریح آماده باشد، اما خروج از مرحلهٔ صفر به پذیرش مالک و مجوز جداگانهٔ گام بعد نیاز دارد.

## ۵. معماری منطقی و مرز اعتماد

```text
مرورگر یا CLI مجاز
  -> nextops-app: ورود محلی، API، worker، جمع‌بندی قطعی، PostgreSQL محدود
  -> nextops-connectors-ro: درگاه MCP دارای هویت و runner جداگانهٔ Zabbix
  -> API مجاز zabbix-server در LAN
  -> nextops-app: شواهد محدود و دارای زمان و دامنه
  -> nextops-ai: فقط شواهد پالایش‌شده، بدون رمز و مسیر مدیریت
  -> nextops-app: پاسخ، منبع، تازگی، مجهول و ممیزی ماندگار
```

مرزهای لازم: کاربر مستقیماً به مدل یا اتصال نمی‌رسد؛ app حساب superuser مشترک ندارد؛ درخواست ابزار دارای هدف ثابت و سیاست و بودجه است؛ runner دوباره روش و مقصد را کنترل می‌کند؛ فقط runner توکن Zabbix را می‌گیرد؛ خروجی مدل دادهٔ غیرقابل‌اعتماد است؛ runtime در شروع به GitHub یا registry وابسته نیست؛ مدیریت ESXi مسیر جدا دارد.

جزئیات تهدیدهای TM-001 تا TM-010 در `docs/requirements/nextops-threat-model.md` آمده است.

## ۶. استقرار، شبکه و ذخیره‌سازی تک‌میزبان

| ترتیب | VM | vCPU | RAM GiB | VMDK GiB | نقش |
|---|---|---:|---:|---:|---|
| ۱ | `nextops-app` | ۸ | ۳۲ | ۲۰۰ | رابط، هویت، API، worker و PostgreSQL محدود |
| ۲ | `nextops-ai` | ۲۴ | ۱۲۸ | ۵۰۰ | یک سرویس مدل CPU محلی |
| ۳ | `nextops-connectors-ro` | ۴ | ۸ | ۸۰ | درگاه MCP و runner فقط‌خواندنی |
| پیش از 1C | `zabbix-server` | ۴ | ۱۶ | ۲۰۰ | پایش، PostgreSQL خودش، frontend/API و Agent 2 |
| مجموع | ۴ VM | ۴۰ | ۱۸۴ | ۹۸۰ | پیشنهاد؛ نه تخصیص و نه benchmark |

فقط reverse proxy برنامه از شبکهٔ کاربر قابل دسترسی باشد. شبکهٔ سرویس، خروجی connector و مدیریت ESXi جدا و با rule واقعی محدود شوند. مدل، مرورگر و app مسیر مستقیم تجهیزات ندارند.

جمع VMDK برابر ۹۸۰ GiB و سهم موقت swap در ESXi برابر ۱۸۴ GiB است؛ جمع اولیه پیش از سربار دیگر ۱۱۶۴ GiB می‌شود. با snapshot فضای آزاد ارسالی DS-C، حدود ۲۰۰۲٫۸۷ GiB آزاد و ۱۱۰۸٫۶۸ GiB بالاتر از حاشیهٔ دقیق ۸۹۴٫۱۸۷۵ GiB می‌ماند. این رزرو نیست. سقف سه‌ترابایتی پروژه و هدف محافظه‌کارانهٔ حدود ۹۰۰ GiB فضای آزاد حفظ شوند. DS-A و DS-B و حجم سیستم تخصیص نگیرند.

## ۸. نامزد مدل و برنامهٔ سنجش CPU

مبنای پیشنهادی یک build ثابت CPU از `llama.cpp` و یک مدل چندزبانهٔ کوانتیزهٔ حدود ۷ تا ۹ میلیارد پارامتر است. Qwen3-8B فقط نامزد ارزیابی است. یک مدل کوچک‌تر برای تأخیر و مدل حدود ۱۴B فقط در صورت کمبود کیفیت مقایسه شوند. embedding تا زمان نیاز RAG عقب می‌ماند.

پس از مجوز: ISA مهمان، build و صفر بودن GPU offload بررسی شود؛ با یک درخواست و corpus ثابت فارسی/انگلیسی/ترکیبی شروع شود؛ ۱۶/۲۴/۲۸ vCPU فقط پس از شناخت topology مقایسه شوند؛ quantization و اندازه روی دادهٔ یکسان سنجیده شوند؛ contextهای لازم و هم‌زمانی ۱، سپس ۲ و ۴ فقط با حفظ پاسخ‌گویی هسته بررسی شوند؛ شروع سرد و آفلاین و بار پایدار ثبت شوند.

TTFT، صف، throughput، p50/p95، حافظه، CPU ready/co-stop، NUMA، swap، خطا، اعتبار schema، منبع شاهد و کیفیت فارسی ثبت شوند. سرعت وعده داده نمی‌شود.

## ۹. بودجهٔ منابع

برای شروع کوچک، یک generation فعال و صف و fan-out محدود پیشنهاد می‌شود؛ اندازهٔ دقیق صف باید در طراحی آزمون 1A تعیین شود. replica، آموزش، reranker و ingestion حجیم در مرحلهٔ یک وجود ندارد.

| چیدمان شامل Zabbix | VM | vCPU | RAM GiB | VMDK GiB | با swap موقت ESXi |
|---|---:|---:|---:|---:|---:|
| مراحل ۱–۲ | ۴ | ۴۰ | ۱۸۴ | ۹۸۰ | ۱۱۶۴ |
| مراحل ۳–۶ با DB جدا | ۵ | ۴۸ | ۲۴۸ | ۱۲۸۰ | ۱۵۲۸ |
| مراحل ۷–۸ با اصلاح | ۶ | ۵۲ | ۲۶۴ | ۱۳۶۰ | ۱۶۲۴ |

تعداد کاربر، هم‌زمانی، host/item، رویداد، حجم شاهد، نگهداری و هدف کیفیت/تأخیر پیش از ادعای ظرفیت عددی شوند.

## ۱۰. هویت، secret، سیاست، تأیید و مدل تهدید

هویت اولیه محلی و تک‌سازمانی است، اما `organization_id` و `environment_id` در رکورد حساس حفظ می‌شوند. نقش‌های `viewer`، `operator`، `engineer` و `admin` با دامنهٔ اقدام و هدف ترکیب می‌شوند. admin میان‌بُر نیست.

سیاست مرحلهٔ یک پیش‌فرض رد، ابزار نام‌دار فقط‌خواندنی، نبود کامل مسیر تغییر، ریسک تعیین‌شده توسط کد معتبر، کنترل هویت و دامنه و بودجه و ممیزی است. رمز فقط از طریق reference و فقط به runner مربوط می‌رسد؛ در Git، prompt، پاسخ، log، audit، screenshot و fixture قرار نمی‌گیرد.

تهدیدهای اصلی: دور زدن دامنه، prompt injection در شواهد، سرقت توکن یا دور زدن gateway، SSRF و جایگزینی مقصد، شکست audit، مصرف منابع، بستهٔ آفلاین آلوده، شاهد قدیمی/ناقص، خرابی تک‌میزبان و جداسازی آیندهٔ چندسازمانی.

## ۱۱. مدل داده، workflow، شاهد، topology و RCA

رکوردهای اولیه شامل سازمان/محیط، کاربر/نقش/دامنه، asset/endpoint، connector/capability، run/step، evidence/link، audit، topology edge، نسخهٔ model/prompt/policy و در آینده proposal/approval/execution هستند.

```text
RECEIVED -> AUTHORIZED -> SCOPED -> PLANNED
 -> COLLECTING -> ANALYZING -> COMPLETED

DENIED | EXPIRED | CANCEL_REQUESTED | CANCELLED | FAILED
```

پیشرفت پیش و پس از تماس خارجی ماندگار شود. لغو محلی اثبات توقف درخواست راه دور نیست. شاهد دارای منبع، روش، هدف، دامنه، فیلتر، زمان جمع‌آوری و اندازه‌گیری، پرچم ناقص/قدیمی، hash و وضعیت پالایش است. شمارش را کد قطعی انجام می‌دهد.

Topology ابتدا رابطه‌ای و دارای منبع و تازگی است. RCA مشاهده و فرضیه و شاهد موافق/مخالف و مجهول را جدا می‌کند و فقط با شاهد کافی علت را تأییدشده می‌نامد.

## ۱۲. نقشهٔ اتصال‌ها و وضعیت قابلیت

Zabbix در مرحلهٔ یک و فعلاً فقط مستند است. Linux مرحلهٔ دو؛ Windows، Cisco، Juniper و Grafana مرحلهٔ سه؛ FortiGate و Sophos مرحلهٔ چهار؛ SQL Server، MySQL/MariaDB و ESXi مرحلهٔ پنج هستند. وضعیت هر قابلیت فقط یکی از `planned`، `simulated`، `lab-verified` یا `production-validated` است.

ابزارهای اول Zabbix محدود به نمای کلی وضعیت، وضعیت host، مشکل فعال و سلامت موتور پایش‌اند. دامنهٔ API نسخه‌سازگار و محدود است؛ write، acknowledge، script و روش دلخواه رد می‌شوند. هیچ placeholder موفق مجاز نیست.

## ۱۳. API، رابط دوزبانه و دسترس‌پذیری

حداقل API شامل session محلی، ساخت idempotent یک run، دریافت وضعیت و evidence، progress احرازهویت‌شده، درخواست cancel و health جداگانهٔ live/ready است. UI حداقل باید ورود، سؤال، پیشرفت، پاسخ، کارت شاهد، زمان/دامنه/تازگی و حالت ناقص/قدیمی/آفلاین/ردشده را نشان دهد.

فارسی طبیعی RTL، انگلیسی LTR و spanهای LTR برای IP و code و timestamp لازم‌اند. assetهای UI محلی‌اند. keyboard، focus، label، contrast و معنای وضعیت مستقل از رنگ آزموده می‌شوند.

## ۱۴. GitHub، CI، انتشار و بازگشت

remote فعلی `Omid-NextAI/nextops` است. `.github` فعلاً فقط قالب و CODEOWNERS دارد و workflow ندارد. حفاظت شاخه و امضا و scanning ادعا نمی‌شوند.

تغییرها کوچک و reviewپذیر باشند؛ PR نامطمئن روی runner موقت بدون مسیر مدیریت اجرا شود؛ Actionها pin و permissionها حداقلی باشند؛ آزمون G10 فقط مسیر معتبر و محدود داشته باشد؛ انتشار tagged دارای lock، SBOM، manifest مدل و checksum باشد؛ promotion دستی و بدون `git pull` زمان boot انجام شود؛ rollback سازگاری app/config/model/database را پوشش دهد.

## ۱۵. آزمون، آفلاین، پشتیبان و معیار آمادگی

فقط بررسی مستندات واقعاً اجرا شد و قبول شد. هیچ آزمون برنامه، پایگاه، API، مرورگر، مدل، connector، Zabbix، ESXi، کارایی، آفلاین، restart یا restore اجرا نشده است.

در ادامه unit، PostgreSQL integration، MCP contract، simulator و API/browser و ارزیابی مدل لازم‌اند. ZBX-01 تا ZBX-08 و OFF-01 تا OFF-10 باید با commit و محیط و نسخه و نمونه و زمان و نتیجهٔ واقعی ثبت شوند.

آزمون آفلاین باید Internet را برای runtime و مرورگر تازه در IPv4/IPv6 و proxy/tunnel مسدود کند، LAN مجاز را نگه دارد و شروع سرد، ورود تازه، لغو توکن، قطع Zabbix، شاهد قدیمی، artifact خراب، بار پایدار و reconnect را پوشش دهد.

پیش از production، مقصد encrypted بیرون میزبان یا رسانهٔ آفلاین کنترل‌شده، RPO/RTO و restore واقعی در محیط جدا لازم است. snapshot همان میزبان DR نیست.

## ۱۶. گام‌های اولویت‌دار و معیار پذیرش

۱. **قرارداد و سیاست رد پیش‌فرض 1A:** پروژهٔ Python ثابت، domain/contracts/policy و unit test؛ بدون connector و credential. معیار: install قفل‌شده، Ruff/mypy/pytest و رد تمام action/target/scope ناشناخته و mutation.

۲. **برش ماندگار app:** هویت محلی، API نسخه‌دار، migration و role پایگاه، run ماندگار، audit و UI/CLI fixture. معیار: request محدود پس از restart حفظ و دسترسی لغوشده رد شود.

۳. **مدل CPU محلی 1B:** artifact مجاز، سرویس داخلی، budget و قرارداد LLM. معیار: پاسخ تازهٔ فارسی/انگلیسی با شروع سرد و Internet قطع، بدون ادعای Zabbix.

۴. **Zabbix و اتصال 1C:** پس از مجوز ساخت، mount/service/self-monitoring، reader محدود و gateway/runner. معیار: شمارش واقعی درست، رد write و عدم نشت token.

۵. **پاسخ کاربردی 1D:** اتصال run، شاهد، محاسبه، مدل، نمایش و audit. معیار: سؤال تازه با منبع و زمان و دامنه و مجهول.

۶. **پذیرش آفلاین 1E:** اجرای ZBX و OFF لازم با نتیجهٔ ثبت‌شده.

## ۱۷. ریسک، مانع و تصمیم لازم مالک

- پذیرش معماری و ADR هنوز انجام نشده و شروع implementation را نگه می‌دارد.
- مجوز ساخت، نصب، شبکه و دسترسی هدف از مرحلهٔ صفر حاصل نمی‌شود.
- ظرفیت جاری، topology، سازگاری VM و سلامت/تعهد DS-C باید خصوصی بررسی شوند.
- روش bootstrap و recovery هویت محلی هنوز تصمیم می‌خواهد.
- نسخه، base path، host group و token Zabbix هنوز اطلاعات استقرار خصوصی‌اند.
- هدف عددی scale، latency و کیفیت هنوز تعیین نشده است.
- فهرست artifact آفلاین و مقصد پشتیبان بیرون میزبان آماده نیست.
- حفاظت GitHub و CI و امضای انتشار آماده/بررسی نشده‌اند.
- نام مخزن در اسناد جاری با remote جدید یکسان نیست و اصلاح نسخه‌دار لازم دارد.
- پیش از سازمان دوم، مدل جداسازی و migration و threat review تازه الزامی است.

این گزارش از مالک می‌خواهد معماری چهارماشینی، مرزهای اعتماد، مسیر 1A تا 1E و برش کوچک زیر را قبول یا اصلاح کند. مجوز زیرساخت باید جداگانه صادر شود.

## ۱۸. کوچک‌ترین تغییر پیشنهادی اول

پس از پذیرش مرحلهٔ صفر، با قرارداد دارای نوع و سیاست رد پیش‌فرض برای `nextops-app` شروع شود، نه با مدل یا توکن واقعی Zabbix.

uv.lock
packages/nextops/domain/

tests/unit/domain/

tests/unit/policy/

این برش فقط سازمان/محیط، هویت و دامنه، هدف ثابت، درخواست بررسی فقط‌خواندنی، تصمیم سیاست، metadata شاهد، خطای دارای نوع، کلاس ریسک و شناسهٔ correlation/idempotency را تعریف می‌کند. credential، connector، فرمان/SQL دلخواه، مدل، migration، VM یا endpoint عمومی ندارد.

معیار پذیرش: محیط قفل‌شده، قبولی Ruff/mypy/pytest، رد همهٔ action و target و scope ناشناخته و mutation، type-check منبع و تازگی شاهد، و آزمون اینکه متن مدل قادر به تغییر سیاست نیست.

پذیرش این گزارش فقط checkpoint معماری مرحلهٔ صفر را می‌بندد؛ هیچ مرحلهٔ برنامه را پیاده‌شده و هیچ دسترسی زیرساخت را مجاز نمی‌کند.
