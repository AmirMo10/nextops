# معماری سامانه و ساختار مخزن

[English](../en/ARCHITECTURE.md) · [فهرست](INDEX.md)

**وضعیت: معماری مرحلهٔ صفر پذیرفته شده و مرزهای برنامه، پنل ایستای دوزبانه، وضعیت ماندگار PostgreSQL، پردازش احرازهویت‌شده روی CPU و اتصال محدود و فقط‌خواندنی Zabbix برای ارزیابی کاربران پیاده و مستقر شده‌اند.** بررسی ماندگار و ممیزی، قطع WAN در مسیر سرور/API و بازیابی پس از راه‌اندازی مجدد ترتیبی شاهد محدود دارند. درگاه کامل MCP، worker عمومی ماندگار، بازیابی و توپولوژی، اصلاح کنترل‌شده، بازیابی مستقل و پذیرش تولیدی هنوز کار آینده‌اند. [مانیفست انتشار](../status/current-release.yaml) و [وضعیت پروژه](../PROJECT_STATE.md) را ببینید.

## تصمیم اصلی

بخش مدیریتی سامانه به‌صورت یک هستهٔ ماژولار ساخته می‌شود. در کنار آن، پردازشگر گردش‌کار ماندگار، درگاه اجراییِ حفاظت‌شده، اتصال‌دهنده‌های فعال و یک سرویس مستقل برای اجرای مدل روی CPU قرار می‌گیرند. هر ماژول الزاماً یک ریزسرویس نیست؛ جداسازی فرایندها باید دلیل مشخصی مانند حفاظت از اطلاعات ورود، محدودسازی شبکه یا کنترل مصرف منابع داشته باشد.

مسیر اصلی چنین است: کاربر یا فرستندهٔ هشدار ← پراکسی TLS ← API و کنسول وب ← گردش‌کار ماندگار ← تحلیل مدل و بازیابی شواهد مجاز ← کنترل سیاست‌ها ← درگاه MCP ← اتصال‌دهندهٔ محدود به مقصد ← زیرساخت مجاز.

PostgreSQL وضعیت کارها، رخدادها، تأییدها، ممیزی و توپولوژی را نگه می‌دارد. فایل‌های مدل و شواهدِ پالایش‌شده در فضای ذخیره‌سازی محلی با دسترسی محدود قرار می‌گیرند.

## مسئولیت اجزا و مرزهای دسترسی

| جزء | مسئولیت | محدودیت الزامی |
|---|---|---|
| رابط وب و API | نشست، اعتبارسنجی ورودی، نمایش تجهیزات و ثبت درخواست | بدون دریافت اطلاعات ورود تجهیزات یا ارتباط مستقیم با اتصال‌دهنده |
| پردازشگر گردش‌کار | برنامه‌ریزی محدود، جمع‌آوری شواهد و ثبت پیشرفت | بدون اعطای مجوز به خود یا دور زدن درگاه |
| سرویس مدل | فهم زبان و تحلیل شواهد | بدون اطلاعات ورود، تماس اینترنتی دلخواه یا دسترسی به شبکهٔ مدیریت |
| موتور سیاست | تعیین قطعی مجوز، ریسک و نیاز به تأیید | بدون تغییر سطح دسترسی به دستور مدل |
| درگاه اجرا | احراز هویت، بررسی مجدد مجوز، ممیزی و محدودسازی | بدون پذیرش اجرای مستقیم و بی‌هویت |
| اتصال‌دهنده | عملیات مجاز همان سامانه و اطلاعات ورود همان مقصد | بدون پویش آزاد شبکه یا دسترسی به تجهیزات نامرتبط |
| PostgreSQL | مرجع معتبر وضعیت کسب‌وکار و گردش‌کار | بدون حساب مدیریتی مشترک میان همهٔ اجزا |

این مرزها باید با هویت سرویس، نقش پایگاه داده، قواعد شبکه، مجوز فایل و کنترل در نقطهٔ اجرا اعمال شوند. صرفاً کشیدن نمودار، جداسازی امنیتی ایجاد نمی‌کند.

## فناوری‌های آغازین

Python 3.12، FastAPI و Pydantic مبنای پیشنهادی بک‌اند هستند. PostgreSQL، SQLAlchemy و Alembic برای ذخیره‌سازی و تغییرات ساختار داده در نظر گرفته شده‌اند. صف کار ابتدا بر PostgreSQL تکیه می‌کند؛ Redis تنها در صورت وجود نیاز اندازه‌گیری‌شده اضافه می‌شود. React، TypeScript و Vite گزینهٔ اولیهٔ رابط کاربری‌اند. بازیابی شواهد با جست‌وجوی واژگانی محلی و در صورت نیاز pgvector انجام می‌شود. مدل مولد از نسخهٔ ثابت و CPU-only ابزار llama.cpp استفاده می‌کند و مدل بردارسازی جداگانه ارزیابی می‌شود.

نسخه‌های سازگار، فایل قفل وابستگی‌ها، شناسهٔ تصویر کانتینر و نسخه و هش مدل باید هنگام پیاده‌سازی بررسی و ثبت شوند. هیچ‌کدام از این بسته‌ها در این مرحله نصب‌شده تلقی نمی‌شوند. PostgreSQL پایگاه دادهٔ عملیاتی اولیه است؛ پشتیبانی داخلی از MySQL یا SQLite تا زمان آزمون واقعی، معادل آن اعلام نمی‌شود.

پوشهٔ `domain` موجودیت‌ها و قواعد بنیادی را بدون وابستگی به ورودی‌وخروجی چارچوب نگه می‌دارد. `application` شامل کاربردها و رابط‌های مورد نیاز آن‌هاست. `infrastructure` این رابط‌ها را پیاده می‌کند؛ جهت وابستگی نباید برعکس شود. قراردادهای درخواست، رویداد و ابزار در `contracts` تعریف می‌شوند. مسیر import و بسته‌بندی باید صریح باشد؛ این درخت به‌تنهایی تنظیمات ساخت برنامه نیست.

پوشه‌های پیاده‌سازی فقط زمانی ایجاد شوند که کد یا قرارداد واقعی دارند. از فایل عامل بسیار بزرگ، ماژول ابزار عمومی بی‌مرز و دیکشنری‌های بدون نوع برای ارتباط بین ماژول‌ها پرهیز شود.

## استقرار روی یک میزبان

پایگاه داده، درگاه‌ها، فضای ذخیره‌سازی، فهرست تجهیزات و اطلاعات ورود محیط‌های توسعه، آزمایشی و عملیاتی باید جدا باشند؛ اما همه همچنان در معرض خرابی همان میزبان‌اند. تنها پراکسی ورودی در دسترس کاربران مجاز قرار می‌گیرد. مدل، پایگاه داده، MCP و مدیریت پایش داخلی می‌مانند.

مسیرهای پیشنهادی و قابل‌تنظیم عبارت‌اند از `/srv/nextops/models`، `/var/lib/nextops` و `/etc/nextops`. پیش از استفاده، دیسک واقعی و مالکیت آن‌ها بررسی شود. Compose و systemd باید قراردادهای یکسان و محدودیت‌های مستند داشته باشند. افزودن Kubernetes، Kafka، مش سرویس، موتور گردش‌کار دوم یا پایگاه دادهٔ گراف به تصمیم معماری مستند نیاز دارد. پشتیبان خارج از میزبان و راه بازیابی دسترسی، شرط ورود به بهره‌برداری‌اند.
