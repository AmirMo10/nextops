# نصب و آماده‌سازی سرور G10

[English](../en/INSTALL.md) · [فهرست](INDEX.md)

**آنچه اکنون قابل انجام است: دریافت مخزن، مطالعهٔ مستندات، اجرای API مبدأ 1A، آزمون قرارداد و مهاجرت پایگاه داده در محیط توسعهٔ جدا، اعتبارسنجی بستهٔ آفلاین سیستم‌عامل برای هر سرور و بازبینی پروفایل مبدأ systemd برای نقش هوش مصنوعی در مرحلهٔ 1B.** اکنون چهار اسکریپت لایهٔ بسته‌ها، پروژهٔ قفل‌شدهٔ Python، نقطهٔ ورود FastAPI، مهاجرت پایهٔ Alembic، کد ماندگار سرویس و واحدهای سخت‌سازی‌شدهٔ مبدأ برای محیط اجرا و API هوش مصنوعی وجود دارند. بااین‌حال بستهٔ تأییدشده، نصب‌کنندهٔ کامل برنامهٔ تولید، انتشار آفلاین، تنظیم reverse proxy، رابط مرورگر، Compose، سرویس اتصال، سرویس مستقر هوش مصنوعی یا بستهٔ آزمودهٔ پشتیبان‌گیری و بازیابی هنوز آماده نیست. مراحل آماده‌سازی میزبان در این صفحه فقط چک‌لیست اجرا هستند و مجوز یا شاهد استقرار محصول به‌شمار نمی‌آیند.

## شروع کار با مخزن

</div>

```bash
git clone https://github.com/Omid-NextAI/nextops.git
cd nextops
git status --short
uv sync --extra dev --frozen
uv run ruff format --check packages migrations tests scripts deploy/installers
uv run ruff check packages migrations tests scripts deploy/installers
uv run mypy packages tests deploy/installers
uv run pytest -m "not integration"
```

<div dir="rtl">

پیش از تغییر میزبان، مشخصات اصلی، معماری، امنیت، برنامهٔ CPU و کار بعدی را بخوانید. اتصال مدیریتی به سرور باید معتبر و مورد تأیید مالک باشد. کلید SSH و رمز عبور را در issue یا مخزن قرار ندهید.

## script بسته‌ها برای هر سرور

scriptهای مسیر [`deploy/installers`](../../deploy/installers) فقط لایهٔ دقیق بسته‌های Ubuntu را برای
`nextops-app`، `nextops-ai`، `nextops-connectors-ro` و `zabbix-server` پوشش می‌دهند. پیش از استفاده
[راهنمای installer](../../deploy/installers/README.md) را بخوانید. هر script به repository محلی و امضاشدهٔ
APT، lock دقیق شامل همهٔ وابستگی‌های غیرمستقیم، و SHA-256 جداگانه و تأییدشدهٔ manifest نیاز دارد.

ابتدا اعتبارسنجی بدون تغییر را روی guest متناظر اجرا کنید:

</div>

```bash
./deploy/installers/install-nextops-app.sh \
  --check \
  --bundle-dir /srv/nextops/import/nextops-app \
  --bundle-manifest-sha256 "$APP_BUNDLE_MANIFEST_SHA256"
```

<div dir="rtl">

اجرای `--apply` یک تغییر جدا و نیازمند تأیید است. مالکیت root و نبود اجازهٔ نوشتن برای group/other روی
bundle، Ubuntu 24.04 روی VMware، مقدار `NEXTOPS_PROVISIONING_AUTHORIZED=YES` و `--change-id` الزامی‌اند.
script فقط lock دقیق و معتبر package را نصب می‌کند، راه‌اندازی خودکار سرویس را می‌بندد و از ساخت خودکار
cluster در PostgreSQL جلوگیری می‌کند. این مرحله محصول را پیکربندی یا اجرا نمی‌کند. چون هنوز bundle واقعی
و lock تولیدی package در مخزن نیست، نصب package تا ساخت و تأیید آن artifactها مسدود می‌ماند.

## شناسایی فقط‌خواندنی میزبان

فرمان‌های زیر فقط روی سرور مجاز و در صورت نصب بودن ابزار اجرا شوند. خروجی‌ها ابتدا محلی بررسی شوند. نام میزبان، نشانی واقعی، نام mount و جزئیات حساس پیش از انتشار حذف یا پوشانده شوند.

</div>

```bash
cat /etc/os-release
uname -r
lscpu
lscpu -e=CPU,CORE,SOCKET,NODE,ONLINE
nproc
free -h
lsblk -o NAME,TYPE,SIZE,FSTYPE,MOUNTPOINTS,ROTA
findmnt
systemd-detect-virt
numactl --hardware
ss -lnt
```

<div dir="rtl">

دو فرمان آخر به‌ترتیب نیازمند نصب قبلی ابزار و توجه به حساسیت اطلاعات درگاه‌ها هستند. نبود `numactl` مجوز نصب آن در مرحلهٔ شناسایی نیست.

سهم واقعی CPU و محدودیت cgroup، RAM آزاد، بارهای موجود، فضای آزاد مسیرهای هدف، هماهنگی ساعت، مسیر شبکهٔ مدیریت و مقصد پشتیبان نیز بررسی شوند. در مرحلهٔ صفر آزمون فشار، پاک‌سازی cache، تغییر firewall یا SSH، پارتیشن‌بندی، راه‌اندازی مجدد و دانلود مدل بزرگ انجام نشود.

Ubuntu نیاز متن اولیه است؛ Ubuntu 24.04 LTS و Python 3.12 فقط مبنای پیشنهادی‌اند و به سازگاری و تأیید مالک وابسته‌اند. نصب دوبارهٔ سیستم‌عامل فرض نشده است. تعداد تجهیزات، حجم رخداد، مدت نگهداری داده، بررسی‌های هم‌زمان و هدف تأخیر باید پیش از برآورد ظرفیت مشخص شوند.

## مسیر آینده با Compose

پس از تأیید release قابل‌استقرار: فایل‌ها بررسی شوند؛ منابع و درگاه‌ها پیش‌بررسی شوند؛ هویت سرویس و مسیرهای محدود ساخته شوند؛ ارجاع به اطلاعات ورود خارج از Git تنظیم شود؛ مدل CPU معتبر وارد شود؛ patch منتخب PostgreSQL آماده شود؛ migrationها به‌ترتیب اجرا شوند؛ حساب محلی بدون رمز پیش‌فرض ایجاد شود؛ سرویس‌های داخلی بالا بیایند؛ سپس پراکسی، سلامت و رد عملیات غیرمجاز آزموده شوند. تنها شبیه‌ساز یا اتصال آزمایشگاهیِ صریحاً مجاز فعال شود.

کانتینر محدود و ترجیحاً غیرریشه، سقف منابعِ آزموده و جداسازی شبکه لازم است. درگاه پایگاه داده، مدل یا MCP عمومی نشود و سوکت موتور کانتینر در اختیار برنامه قرار نگیرد. دستور اجرایی دقیق فقط هنگامی مستند شود که فایل متناظر و آزمون نصب تمیز وجود داشته باشد.

## مسیر بومی با systemd

بسته‌های ثابت و سازگار، محیط مجازی اختصاصی، کاربران سرویس جدا، مسیر داده و تنظیمات محدود و واحدهای مستقل API، worker، gateway و inference در نظر گرفته شوند. وابستگی واحدها، رفتار راه‌اندازی مجدد، سقف منابع، مسیرهای قابل‌نوشتن و محدودیت‌های سخت‌سازی ثبت شوند. معنای تنظیمات و آزمون پذیرش باید با مسیر Compose یکسان باشد.

## نصب آفلاین

در محیط متصل و مجاز، بستهٔ تأییدشده‌ای شامل برنامه، تصویرها یا بسته‌ها، وابستگی‌های غیرمستقیم، دارایی‌های محلی رابط، فایل مدل و tokenizer، migration، راهنما و هش تهیه شود. اطلاعات ورود عملیاتی در بسته نباشد. پس از ورود به محیط آفلاین، صحت فایل‌ها بررسی شود. نبود فایل باید خطای پیش‌بررسی بدهد، نه دانلود خودکار.

با مسدود بودن اینترنت و باز بودن فقط مقصدهای مجاز شبکه، ورود کاربر، اجرای مدل محلی، بازیابی شواهد، عیب‌یابی مجاز و ممیزی آزموده شوند.

## معیار پذیرش استقرار

نسخه و میزبان، نتیجهٔ واقعی آزمون، شاهد اجرای CPU، مجوزها، درگاه‌های در معرض دسترس، ماندگاری ممیزی، بازیابی پس از توقف و نتیجهٔ restore ثبت شوند. مقصد پشتیبان خارج از میزبان، اهداف و سپس اندازه‌گیری RPO/RTO و راه بازیابی دسترسی مدیریتی تعیین شوند. پوشهٔ پشتیبان روی همان سرور فقط محل موقت است. آمادگی عملیاتی پیش از بازبینی شواهد مرحلهٔ هشت اعلام نشود.
